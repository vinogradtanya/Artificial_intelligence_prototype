# Модель жизненного цикла системы

_(оформлено по ГОСТ Р 57193-2025 «Системная и программная инженерия. Процессы
жизненного цикла систем», гармонизирован с ISO/IEC/IEEE 12207)_

## 1. Выбранная модель ЖЦ

Выбрана **итерационная (итеративно-инкрементная) модель** с элементами
**прототипирования**, ориентированная на создание MVP.

Работа разбита на короткие итерации, каждая из которых завершается работающим
инкрементом:

| Итерация | Инкремент | Результат |
|---|---|---|
| 1 | Каркас: БД, аутентификация, кабинет | Работающий вход/профиль |
| 2 | Генерация (mock) + модерация + баланс | Сквозной сценарий |
| 3 | Библиотека, история, отчёты, экспорт | Отчётность |
| 4 | Роль администратора, статистика, аудит | Администрирование |
| 5 | Тесты, документация, испытания | Готовый прототип |

## 2. Обоснование выбора

1. **Требования уточняются по ходу.** В учебном проекте объём ТЗ уточнялся итерационно
   (что реализуемо, что выносим в «перспективу»).
2. **Ранняя обратная связь.** Работающий прототип после каждой итерации позволяет
   демонстрировать прогресс и получать замечания.
3. **Снижение рисков.** Mock-подход убирает зависимость от внешних AI-сервисов.
4. **Ограниченные ресурсы.** Один разработчик и семестр — итерации соразмерны срокам.
5. **Соответствие практике MVP.** Позволяет законно разграничить обязательные и
   перспективные требования (см. ТЗ, раздел 10).

**Альтернативы и почему отклонены:** водопадная модель (требует полного и неизменного
ТЗ — не подходит для учебного уточнения объёма); спиральная (избыточна, акцент на
управлении рисками крупных систем); V-модель (требует строгой верификации на каждом
уровне — избыточно для прототипа).

## 3. Процессы ЖЦ (по ГОСТ Р 57193-2025)

### 3.1. Организационные процессы

- **Управление жизненным циклом:** поэтапное планирование итераций.
- **Управление инфраструктурой:** локальная среда (Python, venv, файловое хранилище).
- **Управление портфелем проектов:** не применяется (один проект).
- **Управление человеческими ресурсами:** роль — один разработчик-студент.
- **Управление качеством:** модульные тесты, ревью кода, испытания.

### 3.2. Технические процессы (основное русло разработки)

| Процесс | Реализация в проекте |
|---|---|
| Анализ требований | Сокращённое ТЗ, перечень Ф-01…Ф-16 |
| Проектирование архитектуры | Клиент-сервер (Flask), слоистая структура `app/` |
| Проектирование компонентов | Модули auth/main/projects/reports/admin, `models.py` |
| Интеграция | Blueprint-модули, единая фабрика `create_app` |
| Верификация | 50 автотестов pytest (см. ПМИ) |
| Валидация | Сверка с ТЗ, демонстрация пользователю |
| Переход (transition) | Развёртывание локально, seed-данные |
| Эксплуатация | Работа пользователя по руководству |
| Сопровождение | Устранение замечаний, доработки |

### 3.3. Процессы технического управления

- **Планирование:** итерации и их содержание (раздел 1).
- **Управление конфигурацией:** версионируемая структура файлов, `.gitignore`,
  изоляция БД (`storage/`), `requirements.txt`.
- **Управление информацией:** документация в `docs/`, README.
- **Управление измерениями:** метрики — число тестов, покрытие функций ТЗ.

### 3.4. Процессы соглашения

- Заказчик (преподаватель) и исполнитель (студент) согласуют объём прототипа:
  обязательные требования реализуются, перспективные — декларируются.
